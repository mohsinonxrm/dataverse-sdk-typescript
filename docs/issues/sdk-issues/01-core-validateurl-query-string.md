# core: validateUrl counts the whole query string as one 260-character "segment", so FetchXML, long $select and nextLink paging throw DataverseUrlError
<!-- labels: bug,P0,pkg:core,fetchxml-studio -->

## Summary

`DataverseRequestBuilder.send()` validates the full URL, **including the query string**, with
`validateUrl()`. `validateUrl()` splits on `/` and rejects any piece longer than 260 characters.
`encodeURIComponent` turns `/` into `%2F`, so the whole query string becomes a single "segment".
As a result, realistic requests throw before they are sent:

- a FetchXML query of about 180 characters (`?fetchXml=…`);
- `$select` with about 20 custom columns;
- following `@odata.nextLink` with a `$skiptoken` paging cookie (`iterate()` / `getAll()`).

The 260-character limit Microsoft documents applies to **path segments** (for example a long
alternate key or function parameter in the path), not to the query string. The query string is
covered only by the total URL limit (32 KB).

## Why FetchXML Studio needs this

Every result grid page is `GET <entityset>?fetchXml=<encoded>`. Metadata calls use long `$select`
lists, and saved views page with `@odata.nextLink`. All of these fail today unless every call
uses `.skipUrlValidation()` or the raw `client.send()`.

## Repro

```js
const c = new DataverseClient({ baseUrl: 'https://org.crm.dynamics.com', fetchProvider: fake, logger: quiet });
const fetchXml = `<fetch top="50"><entity name="account"><attribute name="name"/><attribute name="accountnumber"/><filter><condition attribute="statecode" operator="eq" value="0"/></filter></entity></fetch>`;
await c.api(`/accounts?fetchXml=${encodeURIComponent(fetchXml)}`).get();
await c.api('/accounts').select(...Array.from({ length: 20 }, (_, i) => `new_customattribute${i}`)).get();
for await (const r of c.api('/accounts').select('name').iterate()) {}   // first page returns a nextLink with $skiptoken
```

Actual output (`repro/core.mjs`, cases 1, 1b and 1c):

```
## 1. FetchXML in path via api().get()
THREW DataverseUrlError: URL segment exceeds maximum length of 260 characters (actual: 310).
## 1b. 20-column $select via api().select().get()
THREW DataverseUrlError: URL segment exceeds maximum length of 260 characters (actual: 486).
## 1c. nextLink with long $skiptoken via iterate()
THREW DataverseUrlError: URL segment exceeds maximum length of 260 characters (actual: 407).
```

The same check blocks `MetadataClient` (`repro/gen/03-metadata.mjs`):

```
[getAttributeDefinitions long select] THREW DataverseUrlError: … (actual: 368)            ← 19 attribute properties
[getAttributeDefinitions short select + 300-char filter] THREW DataverseUrlError: … (actual: 327)
```

The validation is also inconsistent. `DataverseClient.execute()` (generated functions) doesn't
validate at all, so a FetchXmlToQueryExpression URL well over 260 characters goes through
(`repro/gen/07-functions-execute.mjs`).

## Root cause

- `packages/dataverse-sdk-core/src/utils/validateUrl.ts:58-61` runs `url.split("/")` over the full URL.
- It is called with the URL including the query string at `packages/dataverse-sdk-core/src/client/DataverseRequestBuilder.ts:327`.
- `PageIterator` (`src/paging/PageIterator.ts`) follows the absolute nextLink through the same builder.

## Proposed fix

- Validate segment length on `new URL(url).pathname` only. Keep the total-length check on the full
  URL.
- When the total length is over the limit for a GET with `fetchXml`, point to the long-query
  fallback (see the FetchXML API issue) in the error message.

## Acceptance criteria

- [ ] The three cases above succeed. A path segment over 260 characters, for example
      `accounts(name='<300 chars>')`, still throws.
- [ ] Unit tests cover a query string well over 260 characters, a nextLink with `$skiptoken`, and
      the total-length limit.

## Workaround in FetchXML Studio until fixed

Call `.skipUrlValidation()` on every request, or use `client.send()` directly.
