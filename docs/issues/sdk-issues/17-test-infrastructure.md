# tests: suites mock the broken boundaries and run only in Node; add fake-fetch contract tests and a browser environment
<!-- labels: testing,P1,fetchxml-studio -->

## Summary

On `f45e6fd`, the suites pass: core 153/153, batch 58/58, xrm 30/30, auth-msal-browser 28/28. Yet
the batch builder, `OrganizationService` CRUD, URL validation for FetchXML and MSAL first sign-in
all fail when exercised end to end (see the linked issues). The causes:

- **The wrong boundary is mocked.** The xrm and batch tests mock `client.api().post()`/`get()` to
  return `Response`-like objects. The real builder returns parsed JSON.
- **Only Node runs.** `vitest.config.ts` sets `environment: "node"`. Nothing runs in a DOM-like or
  browser environment, which is where `auth-msal-browser` and the SPA sample run.
- **No integration tests.** CI runs `turbo run test:integration`, but no package defines it.

## Proposed fix

- Add a shared test helper: `createTestClient({ responses })`, a real `DataverseClient` with a
  recording `fetchProvider` (or MSW, which is already a devDependency).
  - Assert on the wire: method, URL, headers and body.
  - Use recorded Dataverse responses: OData errors, 429 with `Retry-After`, 204 with
    `OData-EntityId`, multipart `$batch`, and FetchXML with paging annotations.
- Add a vitest `browser` (Playwright) or `happy-dom` project for `auth-msal-browser` and
  core-in-browser checks: no `Buffer`, `new Function` or `process`.
- Add a smoke test that bundles each browser package with Vite and loads it in Chromium.
- Optionally, add an opt-in live suite (`DATAVERSE_URL` plus a token from the Azure CLI) for
  releases.

      pass after the fixes.
