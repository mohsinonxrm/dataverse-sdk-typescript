# core: retry controls don't work as documented (per-request middlewareOptions ignored, Retry-After not capped by maxDelayMs, jitter never applied, network errors not retried)
<!-- labels: bug,P0,pkg:core,fetchxml-studio -->

## Summary

1. **Per-request overrides are ignored.** `RequestOptions.middlewareOptions` is declared
   (`abstractions/options.ts:52`, `abstractions/http.ts:71`), but the builder never copies it to
   the request, and `RetryMiddleware` reads `ctx.middlewareOptions`. `ctx` is the client-wide
   context, which is never set.
2. **`Retry-After` is not capped by `maxDelayMs`.** A `Retry-After: 300` makes a request wait
   5 minutes even with `maxDelayMs: 1000`, with no way for the caller to give up early. Dataverse's
   service protection window is 5 minutes.
3. **Jitter is unreachable.** It applies only if `useExponentialBackoff && jitter`, and
   `useExponentialBackoff` cannot be set through `DataverseClientOptions.retry`.
4. **Network errors are not retried or wrapped.** When `fetch` throws, for example
   `TypeError: Failed to fetch`, the raw error propagates. `DataverseNetworkError` exists but is
   never used.
5. On retries the middleware adds a non-standard **`Retry-Attempt` request header**. Cross-origin,
   that needs a CORS preflight allowance (see the telemetry-headers issue).

## Why FetchXML Studio needs this

FetchXML Studio owns throttling itself (`throttleRetry.ts`): two policies, progress text, and a
connection guard that must run before every resend (#96, #175, #183 in FetchXML Studio). It has to
either turn SDK retries off per request, or cap them, without the SDK waiting minutes behind its
back.

## Repro (`repro/core.mjs`, cases 5b, 5d and 10)

```
## 5b. Retry-After not capped by maxDelayMs          (maxDelayMs: 50, Retry-After: 2)
 { calls: 2, waitedMs: 2004, retryAttemptHeader: '1' }
## 5d. per-request middlewareOptions (retry override) ignored   (client maxRetries 2, request maxRetries 0)
 { calls: 3, expected: 1 }
## 10. network error (fetch throws) not retried
 { calls: 1, error: 'TypeError' }
```

`retry: { maxRetries: 0 }` at the client level **does** work (case 5, 1 call). That is the
setting FetchXML Studio will use.

## Root cause

- `packages/dataverse-sdk-core/src/middleware/RetryMiddleware.ts:27`: reads `ctx.middlewareOptions`.
- `RetryMiddleware.ts:68`: `retryAfterMs ?? backoff(...)`, with no cap.
- `RetryMiddleware.ts:70`: the `useExponentialBackoff` guard.
- `RetryMiddleware.ts:42`: the `Retry-Attempt` header.
- `DataverseRequestBuilder.ts:353-361`: `options.middlewareOptions` is not forwarded.

## Proposed fix

- Forward `options.middlewareOptions` onto `RequestInformation`, and read it from the request
  instead of the shared `ctx`.
- Cap waits with `maxRetryAfterMs` (default `maxDelayMs`). When `Retry-After` is longer, return the
  429 immediately (`DataverseThrottleError.retryAfterMs` is already set) instead of sleeping.
- Apply jitter to backoff by default (`jitter: true` already exists in DEFAULTS).
- Wrap `fetch` rejections (except aborts) in `DataverseNetworkError`, and make retrying them opt-in
  for idempotent methods.
- Make the `Retry-Attempt` header opt-in.
