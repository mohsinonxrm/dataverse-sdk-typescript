# core: query strings are re-serialized with URLSearchParams ('+' for spaces, %24 for '$', %27 for quotes); verify against Dataverse and use encodeURIComponent semantics
<!-- labels: question,P2,pkg:core,needs-verification -->

## Summary

`buildUrl()` calls `new URL(req.url).searchParams.set(...)` for every builder option. Setting any
search param re-serializes the **whole** query string with `application/x-www-form-urlencoded`
rules, including query text the caller had already encoded in the path:

```
input : /accounts?$filter=name%20eq%20'O''Brien%20%26%20Co'   + .select('name')
sent  : /accounts?%24filter=name+eq+%27O%27%27Brien+%26+Co%27&%24select=name
```

That is the output of `repro/core.mjs`, case 13. `client.send({ query: { fetchXml } })` produces
`+` for spaces in the same way.

Form encoding is legal URL syntax, and ASP.NET usually decodes `+` as a space. Still, OData's
ABNF and Microsoft's Dataverse samples use `%20` and a literal `$`. Function parameter aliases
(`@p1='…'`) and `$filter` string literals are where differences appear. This needs a live check
before FetchXML Studio relies on it.

## Proposed fix

- Build the query string yourself with `encodeURIComponent` per value, and keep `$` and `@`
  literal in names.
- Append it without re-encoding a caller-supplied query string.
- Add tests for `'`, `&`, `+`, `#`, `%` and non-ASCII values in `$filter`, FetchXML and function
  aliases.

## Acceptance criteria

- [ ] A live check (or documentation) confirms Dataverse treats both forms identically, **or** the
      SDK switches to `encodeURIComponent` semantics.
- [ ] Caller-encoded query strings are left untouched.
