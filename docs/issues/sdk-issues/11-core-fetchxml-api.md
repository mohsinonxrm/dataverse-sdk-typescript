# core: add first-class FetchXML query support (paging cookie, morerecords, total count, formatted values, long-query fallback)
<!-- labels: enhancement,P1,pkg:core,fetchxml-studio -->

## Summary

The SDK has no FetchXML API. The non-generated sources contain no handling of `fetchXml`,
`@Microsoft.Dynamics.CRM.fetchxmlpagingcookie`, `@Microsoft.Dynamics.CRM.morerecords`,
`@Microsoft.Dynamics.CRM.totalrecordcount` or `totalrecordcountlimitexceeded`. `PageResponse<T>` is
just `{ value, @odata.nextLink }`. The SPA sample's FetchXML page
(`samples/spa-fluentui-v9/src/pages/AdvancedQuerying/index.tsx:194-195`) uses
`client.api('/accounts?fetchXml=…').get()`, which throws `DataverseUrlError` for any realistic
query (see the validateUrl issue).

## Why FetchXML Studio needs this

FetchXML is the product. FetchXML Studio already has its own paging state machine (`paging.ts`),
so it needs a **single-page primitive**, not a paging loop.

## Proposed API

```ts
interface FetchXmlPage<T> {
  value: T[];
  pagingCookie?: string;           // raw @Microsoft.Dynamics.CRM.fetchxmlpagingcookie
  moreRecords?: boolean;           // @Microsoft.Dynamics.CRM.morerecords
  totalRecordCount?: number;       // @Microsoft.Dynamics.CRM.totalrecordcount (-1 when not requested)
  totalRecordCountLimitExceeded?: boolean;
  nextLink?: string;               // saved/user query execution pages with nextLink
}
client.fetchXml<T>(entitySetName: string, fetchXml: string, options?: RequestOptions & {
  annotations?: "*" | string[];    // default "*" (formatted values, lookuplogicalname, associatednavigationproperty)
  maxUrlLength?: number;           // default ~30_000; longer queries go through POST $batch with one inner GET
}): Promise<FetchXmlPage<T>>;
client.savedQuery<T>(entitySetName, savedQueryId, options?): Promise<FetchXmlPage<T>>;  // ?savedQuery=
client.userQuery<T>(entitySetName, userQueryId, options?): Promise<FetchXmlPage<T>>;    // ?userQuery=
```

Notes:

- Encode with `encodeURIComponent` (`%20`, not `+`) to match Microsoft's samples. See the
  query-serialization note in the URL-encoding issue.
- The long-query fallback needs the raw-body and batch fixes. Microsoft documents `$batch` as the
  way to send a GET that is longer than the URL limit.
- Optionally add `parsePagingCookie()` / `buildPagedFetchXml(fetchXml, page, cookie)` helpers.
  Keep them pure: FetchXML Studio has its own, but other consumers would benefit.
