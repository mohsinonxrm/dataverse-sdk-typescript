# messages (generator): response parsers read data.value for complex-type and entity returns, so results are always undefined (QueryExpressionToFetchXml, ExecuteWorkflow, …); the response type references itself
<!-- labels: bug,P1,pkg:messages,generator -->

## Summary

The generated `*Response.fromResponse` / `parseResponse` always reads `(data as any).value`. In
OData JSON, only primitive and collection returns are wrapped in `value`. A complex-type return
(for example `QueryExpressionToFetchXmlResponse { FetchXml }`) or a single entity (ExecuteWorkflow
returns an `asyncoperation`) is the response object itself. 962 of the 1361 message files use this
pattern.

The response class is also self-referential: `constructor(public result: QueryExpressionToFetchXmlResponse)`,
because the CSDL return-type name equals the generated class name.

## Repro (`repro/gen/06-entityref-and-messages.mjs`)

```js
new QueryExpressionToFetchXmlRequest({…}).parseResponse(json({ FetchXml: '<fetch>…' }))
```

```
QueryExpressionToFetchXmlResponse.result = undefined | r.FetchXml = undefined
ExecuteWorkflowResponse.result = undefined
```

The `actions` package's equivalents pass the data through correctly (`repro/gen/02-actions.mjs`:
`QueryExpressionToFetchXml.parseResponse -> { FetchXml: '<fetch/>' }`), so this is a messages-only
template bug.

## Root cause

`tools/generate-sdk-types/src/generators/messages-generator.ts:283-293`

## Proposed fix

- Complex-type returns: `result = data`, or spread its properties.
- Entity returns: `result = data` without the `@odata.*` keys.
- Primitive and collection returns: `data.value`.
- Import the complex type under an alias to avoid the name collision.

Alternatively, consider deprecating `messages` in favour of `actions` and `functions`: the two
overlap.

## Acceptance criteria

- [ ] `QueryExpressionToFetchXmlRequest.parseResponse` exposes `FetchXml`.
- [ ] `ExecuteWorkflowRequest` exposes `asyncoperationid`.
