# auth-msal-browser: make @azure/msal-browser a peerDependency and support the current major (v4+); today v3 is bundled as a regular dependency
<!-- labels: enhancement,P1,pkg:auth-msal-browser,browser,fetchxml-studio -->

## Summary

`@azure/msal-browser` is a regular dependency pinned to `^3.0.0` (lock: 3.30.0). A browser app
creates its own `PublicClientApplication` (redirect handling, sign-in UI) and passes it to the
provider. If the app uses msal-browser v4 (current; the repo's own lock already contains 4.28.1
for other packages), the bundle ships **two MSAL copies**. `instanceof InteractionRequiredAuthError`
then fails across them, and the error classes don't match.

## Why FetchXML Studio needs this

FetchXML Studio's web build owns sign-in (popup and redirect, account switching, a "bring your own
client ID" option) and must share one MSAL instance and cache with the SDK provider.

## Proposed fix

- Move `@azure/msal-browser` to `peerDependencies` (`">=3.30 <6"`, or whatever range is tested),
  with a devDependency for tests.
- Use duck typing (`error.errorCode`, `error.name`) instead of `instanceof` across the package
  boundary.
- Test against v3 and v4.

## Acceptance criteria

- [ ] An app on msal-browser v4 gets one copy in its bundle (`npm ls @azure/msal-browser`).
- [ ] Interaction-required detection works with an app-created PCA.
