Lower concurrency on Dataverse's concurrent-requests 429, adaptive throttling outside the concurrency slot, and bounded queues (#477).

- **`concurrency.reduceOnThrottle` (default `true`).** A 429 with error `0x80072326` (too many concurrent requests per user, per web server) halves the concurrency limit, not below `min`. One burst of such 429s halves it once. The limit stays down until the 429's `Retry-After` has passed; then the next `x-ms-dop-hint` sets it again as before, or, where the hint isn't readable (browsers, `adaptiveFromDopHint: false`), each successful response raises it by 1 back to where it was. The other service-protection 429s leave the limit alone. On by default because it is a fix: the service has said the client sends too many requests at once, and keeping the limit means the retries of those requests come back at the same concurrency and are throttled again. It changes nothing until that error comes, and then only for about the `Retry-After` the service asked for, so the cost is a short dip in parallelism where the alternative is more 429s. `reduceOnThrottle: false` keeps the 2.0 behaviour. To read the error code, the concurrency middleware reads (a clone of) the body of a JSON 429, as the telemetry middleware already does when telemetry is on.
- **`dataverse.concurrency.limit`** now also fires for these changes, with a new `concurrency.reason` property: `dop_hint`, `throttle` or `recovery`. `dop_hint` is a measurement only when the response had the header.
- **`adaptiveThrottling` client option** (`adaptiveThrottling: new AdaptiveThrottlingMiddleware({ ... })`; default none). It takes an instance, not settings, so clients that don't use it don't bundle it. It places adaptive throttling inside Retry (it sees every attempt's response) and outside Concurrency, so a request it holds back (up to `maxPauseMs`, 30 s by default, after a 429) holds no concurrency slot and no access token, and the wait isn't counted in the attempt's dependency duration. Default order: ODataHeaders, Retry, AdaptiveThrottling, Concurrency, Auth, Telemetry, Logging. Adding the middleware with `middleware.append` / `prepend` still works as before; the client logs a warning once (with a `logger`) recommending the option.
- **`dataverse.throttle.delay` event** for each wait of adaptive throttling (in either placement): properties `request.method`, `throttle.reason` (`pressure`, `retry-after`); measurements `delay_ms`, `throttle.pressure`.
- **`concurrency.maxQueue` (default unbounded).** At most this many requests wait for a concurrency slot; one more is refused at once, without being sent, with the new `DataverseQueueFullError` (`queue: "concurrency"`, `maxQueue`, `queued`, `inFlight`, `limit`). `DataverseBulkheadRejectedError` is now a `DataverseQueueFullError` too (`queue: "bulkhead"`), with the same details, so one `instanceof` check covers both queues. Defaults are unchanged; for servers, the docs recommend setting a bound.
