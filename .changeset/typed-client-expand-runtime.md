`EntitySetClient` types `expand` and narrows reads to the selected columns (#431). A fifth type argument, the table's navigation properties (`SingleNavigation<Contact, ContactColumn, ContactNavigation>` / `CollectionNavigation<…>` / `ManyToManyNavigation<…>` members, which `dataverse-gen` generates as `<Entity>Navigation`), makes `expand` take an object keyed by navigation property, `true` or nested options checked against the related table (`select`, `expand`, and on a collection `filter`, `orderBy`, `top`); the array of names (with inline options) still works. The options follow what Dataverse accepts: `orderBy` / `top` only on a collection, and not together with a nested `expand` or inside another expansion (0x80060888); no nested `expand` inside a many-to-many collection. `get()` and `list()` now resolve `ReadResult<TEntity, TNavigation, TOptions>`: with a literal `select`, only those columns (plus annotations such as `@odata.etag`); each expanded property is the related record or `null` (a lookup) or an array of them (a collection), narrowed by its own options. New exports: `SingleNavigation`, `CollectionNavigation`, `NavigationProperty`, `UntypedNavigation`, `Expand`, `ExpandPropertyOptions`, `ReadResult` and its parts (`SelectedColumns`, `WithoutProperties`, `ExpandedNames`, `ExpandedProperties`, `ExpandedValue`), `RecordAnnotations`. The requests are unchanged: an object `expand` sends what core's `expand(name, options)` sends.

**Breaking.** (types only) A read with a literal `select` no longer has the columns it didn't select, so code that read one (it was `undefined` at runtime) stops compiling: add the column to `select`. A narrowed record is still assignable to the table's interface. Without the fifth type argument, `expand` takes any name and the result keeps the interface's types, as before.
